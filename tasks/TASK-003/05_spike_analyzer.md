## Находка 1 — лимит сообщения ровно 4 MiB (дефолт gRPC)

| Размер запроса | Результат |
|---|---|
| 0.36 МБ | ✅ OK, 2.3 с |
| 2.46 МБ | ✅ OK, 3.2 с |
| 6.38 МБ | ❌ `RESOURCE_EXHAUSTED` за 0.8 с |

Текст ошибки сервера: `SERVER: Received message larger than max (6687802 vs. 4194304)`.

**Вывод:** сервер свой лимит НЕ поднимал — 4 194 304 байт на всё сообщение (включая `photo_id`, `object_key` и служебные поля protobuf). Поднятие лимита на клиенте не поможет: ограничивает приёмная сторона, повлиять на неё мы не можем.

**Следствие для дизайна.** Текущий `MAX_FILE_SIZE_BYTES = 50 МБ` несовместим с прямой отправкой байтов. Варианты (решает architect):
- **(а)** снизить лимит загрузки до ~3.5–4 МБ — просто, но заметно режет продукт;
- **(б)** хранить оригинал в MinIO как есть (до 50 МБ), а анализатору слать уменьшенную копию — продукт не страдает, но в worker появляется зависимость обработки изображений и время на пережатие;
- **(в)** гибрид: слать оригинал, если он влезает, иначе уменьшать.

Рекомендация оркестратора — **(б)/(в)**: уменьшение перед анализом это стандартная практика для детекции лиц и оценки резкости, а лимит загрузки для пользователя остаётся прежним.

## Находка 2 — `RESOURCE_EXHAUSTED` подтверждает риск ретраев

Превышение размера приходит именно как `RESOURCE_EXHAUSTED`, который в нашем `classify_grpc_error` отнесён к **RETRY**. То есть сейчас заведомо безнадёжный запрос будет повторён 3 раза с backoff и лишь потом уйдёт в `failed` с невнятным кодом.

**Требование:** отделить «сообщение слишком большое» (постоянная ошибка → NO_RETRY, `last_error_code = MESSAGE_TOO_LARGE`) от троттлинга (временная → RETRY). Отличать по тексту detail (`Received message larger than max`) либо по предварительной проверке размера до отправки.

## Находка 3 (КРИТИЧНО) — семантика `blur_score` инвертирована

`model_version = opencv-dnn-res10-ssd+laplacian+phash/1.1.0` — резкость считается через **дисперсию лапласиана**, где **больше = резче**.

Замеры на синтетике:

| Кадр | blur_score | is_blurred |
|---|---|---|
| резкий | 99 773.999 | True |
| размытие r=4 | 2.926 | True |
| размытие r=12 | 0.375 | True |

Замеры на настоящей фотографии:

| Кадр | blur_score | is_blurred |
|---|---|---|
| оригинал | 930.47 | True |
| размытие r=6 | 1.10 | True |

**Следствие 1.** Наша формула лучшего кадра сортирует `blur_score` ПО ВОЗРАСТАНИЮ (заглушка отдавала 0…1, где меньше = лучше). С реальным анализатором это выберет **самый размытый кадр** — главная продуктовая фича сработает наоборот.
→ Направление ключа обязано стать **по убыванию** (`blur_score DESC`, больше = резче). Диапазон значений не 0…1, а неограниченный положительный.

**Следствие 2.** Поле `is_blurred` в тестах **не различает** резкое и размытое — вернуло `True` во всех пяти замерах, включая кадр с blur_score 99 774. Тег `blurry` тоже стоял всегда. Как первый ключ сортировки поле бесполезно и может активно вредить.
→ Варианты: убрать `is_blurred` из формулы и опираться на `blur_score`; либо считать «размытость» самим (порог по `blur_score`). Решает architect. Отдельно: стоит сообщить автору анализатора — похоже на баг на его стороне.
