00

Как читать этот гайд

Ты приходишь из олимпиадного питона, где программа — это «считал ввод, посчитал, вывел, завершилась». Бэкенд устроен иначе: это программа, которая запускается и живёт вечно, ожидая запросов по сети, и обслуживает много клиентов одновременно. Почти весь незнакомый синтаксис и вся «лишняя» сложность существуют ради этих двух фактов.

Гайд построен слоями: сначала общая картина и понятия (разделы 1–5), потом разбор каждого файла по слоям (разделы 6–17), в конце — две сквозные истории целиком (раздел 18). Если запутаешься в файле — вернись к разделу 4 «Архитектура» и вспомни, за что отвечает его слой.

Через весь проект проходит один мотив — жизненный цикл фотографии. Держи его в голове, всё крутится вокруг него:

pending→ processing→ done /failed

pending фото загружено, ждёт анализа · processing воркер взял его в работу · done анализ готов · failed анализ не удался. Всё, что делает система, — это переводит фото по этой цепочке и хранит результат.

01

Что это за проект, с нуля

Представь облачное хранилище фото (упрощённое «Облако Mail»). Пользователь загружает картинку, а сервис должен: сохранить её, прогнать через анализатор (сколько лиц, размыто ли, «отпечаток» изображения) и отдать результат. Анализатор — внешняя нейросеть (пока в разработке, у нас вместо неё заглушка).

Из чего состоит система

Когда ты запускаешь docker compose up, поднимается восемь отдельных программ (контейнеров), каждая в своей «коробке», общающихся по сети:

apiнаш Python-код (FastAPI). Принимает HTTP-запросы: загрузить фото, узнать статус, скачать.
workerнаш же код, но другой вход. Не слушает HTTP — читает задачи из очереди и гоняет анализ.
postgresбаза данных. Хранит метаданные: id фото, имя, статус, результат анализа. Как надёжный Excel с языком запросов SQL.
minioобъектное хранилище (аналог Amazon S3). Хранит сами байты картинок — база для больших файлов не годится.
kafkaочередь сообщений. Передаёт задачи «проанализируй фото X» от api к worker, не заставляя api ждать.
analyzer-stubзаглушка нейросети. Отдельный gRPC-сервис, возвращает правдоподобные результаты. В будущем заменится на реальную нейронку.
prometheusсборщик метрик. Периодически опрашивает api и worker и копит числа: сколько загружено, сколько ошибок.
grafanaрисует графики по данным Prometheus — дашборд состояния системы.

Метафора: ресторан

Проще всего думать о сервисе как о ресторане, а о запросе — как о заказе:

  • api — зал с официантами: принимают заказ, отдают ответ. Логику не готовят.
  • services — шеф-повар: вся бизнес-логика (проверить файл, скоординировать хранилище и БД).
  • repositories — кладовщик: единственный, кто ходит на склад (БД). SQL живёт только у него.
  • integrations — курьеры до внешних систем (MinIO, Kafka, анализатор).
  • worker — вторая кухня, работающая «в фоне» по заказам из очереди.
  • core — администрация: устав (конфиг), журнал (логи), книга жалоб (ошибки).

Смысл дробления на роли: можно нанять второго официанта (масштабировать api), заменить склад (поменять БД) и проверять повара отдельно от официанта (тестировать по кускам). Один файл — одна ответственность, и роли общаются строго по правилам.

02

Синтаксис не из олимпиад

Быстрый словарь конструкций, которые встретятся ниже. Если что-то знакомо — пропускай.

Классы и self — данные + функции в одной коробке

Класс склеивает данные и функции, которые с ними работают. PhotoService(repo, storage) создаёт объект (коробку), заполняя его методом __init__. Внутри методов self — «эта самая коробка» (как this в C++, только пишется явно первым параметром). self._repo — данные из коробки; подчёркивание значит «внутреннее, снаружи не трогать».

class PhotoService:
    def __init__(self, repository, storage):   # конструктор коробки
        self._repository = repository            # инструменты кладём внутрь
        self._storage = storage
    async def create_photo(self, ...):           # метод = функция при коробке
        ...

Наследование — «такой же, но с отличиями»

class NotFoundError(AppError) читается «NotFoundError умеет всё, что AppError, но кое-что переопределяет». Ловушка на AppError ловит и всех наследников (кошка — тоже животное).

Декораторы @ — наклейка на функцию

Строчка с @ над функцией «регистрирует» её или оборачивает. @router.post("/v1/photos") = «когда придёт POST на этот путь — зови эту функцию». @lru_cache — мемоизация (та самая, что в динамике). Спрашивай не «что за синтаксис», а «куда её регистрируют / чем оборачивают».

Аннотации типов — подсказки, которые работают

photo_id: uuid.UUID, -> PhotoResponse, str | None («строка или ничего»). Python их не проверяет сам, но FastAPI и Pydantic читают их и на их основе валидируют вход и строят документацию. Прислали не-UUID в аннотированный uuid.UUID — FastAPI сам вернёт ошибку 422.

async / await — кооперативное ожидание

Сервер 95% времени ждёт (БД, сеть, диск). async def — функция, которую можно ставить на паузу; await x — «жду x, а пока пусть работают другие запросы». Так один процесс тянет тысячи соединений. Два следствия: (1) блокирующий код в async замораживает всех — синхронные вызовы оборачивают в anyio.to_thread.run_sync(...); (2) ждать без предела нельзя — async with asyncio.timeout(60):.

Исключения — способ общения, а не «программа упала»

raise NotFoundError(...) «выбрасывает» сигнал, который летит вверх по вызовам, пока кто-то не поймает except. finally выполнится всегда. from exc прицепляет первопричину для логов. В нашем проекте ошибку бросают глубоко внизу, а ловит её один обработчик наверху и превращает в HTTP-код.

with, yield, Depends

async with SessionLocal() as s: — «открой ресурс, дай как s, гарантированно закрой в конце». yield в функции-зависимости — «сделай до, отдай значение, доделай после». Depends(get_session) в параметрах ручки — маркер «FastAPI, вызови get_session и подставь результат сюда»: функция не создаёт инструменты сама, ей их приносят (это внедрение зависимостей; в тестах приносят подделки).

03

Новые понятия конвейера (TASK-002)

До этого сервис был синхронным: загрузил — сразу ответ. Теперь появляется асинхронная обработка: загрузка мгновенна, а тяжёлый анализ идёт в фоне. Для этого вводится несколько идей.

Очередь сообщений и Kafka

Очередь позволяет одному сервису передать работу другому без ожидания результата. api не держит HTTP-запрос открытым, пока крутится анализ, — он бросает «задачу» в очередь и сразу отвечает пользователю. Плюсы: анализатор может временно падать, воркеров можно масштабировать отдельно, задачи не теряются при падении воркера.

Kafka технически — распределённый журнал событий, но для нас это очередь задач. Ключевые слова:

topicименованный поток сообщений. У нас — photo.analysis.requested.
producerкто пишет в топик. У нас — api (точнее, фоновый outbox).
consumerкто читает. У нас — worker.
offsetномер последнего обработанного сообщения. Воркер «коммитит» его, чтобы не читать одно и то же дважды.
consumer groupесли воркеров несколько, Kafka делит между ними работу.

В сообщении лежит не файл, а лишь ссылка: {photo_id, object_key, created_at, trace_id}. Сам файл — в MinIO.

gRPC — как воркер зовёт анализатор

gRPC — способ двум сервисам вызывать функции друг у друга по сети, строго по заранее описанному контракту (файл .proto). Воркер шлёт анализатору object_key, получает {faces_count, is_blurred, blur_score, perceptual_hash}. Анализатор ничего не знает про Kafka и статусы — он просто анализирует картинку.

Идемпотентность и защита от гонок

Kafka даёт «at-least-once»: сообщение может прийти более одного раза (например, воркер упал сразу после обработки, не успев закоммитить offset). Значит обработка должна быть идемпотентной — повтор не должен навредить. Ещё два воркера могут схватить одно фото. Решение — атомарный захват:

UPDATE photos SET status='processing'
WHERE photo_id=:id AND status='pending';
# обновилась 1 строка → этот воркер победил
# обновилось 0 строк → задачу уже забрали, пропускаем

Retry с классификацией

Бесконечно повторять нельзя. Временные ошибки (таймаут, анализатор недоступен, сеть) повторяем с лимитом (3 попытки, паузы 1-2-4 сек). Постоянные (не изображение, ошибка валидации) — сразу в failed, повтор бессмыслен.

Outbox — почему загрузка не зависит от Kafka

Если Kafka лежит в момент загрузки, api не должен падать. Приём outbox: при загрузке в БД ставится пометка «событие надо отправить» (publish_status = not_sent). Отдельная фоновая задача периодически берёт такие строки и дошлёт их в Kafka, помечая sent. Загрузка мгновенна и надёжна, даже если очередь временно недоступна.

Метрики, Prometheus, Grafana

Метрика — число о состоянии системы (сколько загружено, сколько ждёт, сколько ошибок). Сервисы отдают их по адресу /metrics, Prometheus периодически их забирает и хранит по времени, Grafana рисует графики. Самый важный график — pending photos over time: если растёт, значит воркер не успевает.

04

Архитектура и слои

Код нарезан на слои, и зависимости текут строго в одну сторону. Ручка (HTTP) не пишет SQL и не лезет в MinIO сама — она зовёт сервис; сервис зовёт репозиторий и интеграции; SQL живёт только в репозитории.

api  →  services  →  repositories  →  db
       ↘ integrations (MinIO, Kafka, gRPC)
core / schemas — поперечные, доступны всем, сами ни от кого сверху не зависят
api/«приёмная»: принять HTTP, вернуть HTTP. Без логики.
services/«мозг»: бизнес-правила, координация БД + хранилища + очереди.
repositories/«кладовщик»: только запросы к БД. Весь SQL здесь.
db/описание таблиц (модели) и подключение к БД.
integrations/общение с внешними системами: MinIO, Kafka, gRPC-анализатор, метрики.
schemas/«бланки» — форма JSON, который принимает и отдаёт API.
core/поперечное: конфиг, логи, ошибки.
worker/отдельный вход в приложение: цикл чтения очереди.

Правило зависимостей окупается именно в тестах: раз сервис получает свои инструменты через конструктор, в тесте ему подсовывают подделки (моки) вместо настоящих БД и MinIO — поэтому 367 тестов бегут за секунды без всякой инфраструктуры.

05

Два путешествия запроса

В проекте два независимых потока. Держи их отдельно — тогда все файлы встанут на места.

Путешествие A — загрузка (синхронное, мгновенное)

api / ручка
POST /v1/photos, читает байты файла, зовёт сервис.
service
проверяет magic bytes, создаёт запись, кладёт байты в MinIO.
БД + MinIO
строка со статусом pending и пометкой not_sent; файл в хранилище.
ответ 202
пользователь сразу получает photo_id и статус pending.

Заметь: Kafka здесь не участвует. Загрузка ничего не ждёт от очереди.

Путешествие B — анализ (асинхронное, в фоне)

outbox
фоновая задача в api видит not_sent, шлёт событие в Kafka, ставит sent.
kafka
хранит задачу {photo_id, object_key,...} в топике.
worker
читает, атомарно захватывает pending→processing.
gRPC → analyzer
шлёт object_key, получает результаты анализа.
БД
пишет analysis_results, статус done (или failed после ретраев).

Теперь GET /v1/photos/{id} вернёт done с заполненным analysis. Всё это время каждый шаг логируется с общим trace_id, пришедшим из сообщения.

06

core: фундамент

Поперечные модули, которыми пользуются все слои: конфиг, логи, ошибки.

app/core/config.pyконфиг

Единый источник всех настроек. Класс Settings(BaseSettings) — «магический»: при создании сам читает переменные окружения и файл .env и заполняет поля. Дефолты подобраны под docker-compose (хосты postgres, kafka, minio), так что всё работает даже без .env.

get_settings() → SettingsОбёрнута в @lru_cache: настройки парсятся один раз за процесс, дальше все получают тот же объект (синглтон, дёшево).

TASK-002 добавил сюда блок Kafka (KAFKA_BOOTSTRAP_SERVERS, KAFKA_TOPIC_ANALYSIS_REQUESTED, KAFKA_CONSUMER_GROUP), адрес анализатора (ANALYZER_GRPC_ADDR), параметры ретраев (WORKER_MAX_ATTEMPTS=3, RETRY_BACKOFF_BASE_SECONDS=1), порт метрик воркера и настройки outbox (OUTBOX_POLL_INTERVAL_SECONDS, OUTBOX_BATCH_SIZE).

app/core/logging.pyлоги + трассировка

Логи пишутся в stdout как JSON — так их собирает контейнерная платформа. Главная хитрость — сквозной request_id/trace_id, чтобы по одному id найти все строки одного запроса.

trace_id_var: ContextVar«Глобальная переменная, у которой в каждой одновременной задаче своё значение». Обычная глобальная сломалась бы — два параллельных запроса перезаписали бы id друг друга.
class TraceIdFilterКрючок, срабатывающий на каждую строку лога: дописывает в неё trace_id, request_id (одно значение под двумя именами) и имя сервиса.
setup_logging(level)Настраивает корневой логгер: чистит старые обработчики (чтобы в тестах строки не двоились), вешает JSON-форматтер и фильтр. Воркер зовёт эту же функцию — трассировка у api и worker единообразна.
app/core/errors.pyошибки → HTTP

На каждую ожидаемую неприятность — свой класс-исключение, знающий свой HTTP-код. Код просто делает raise NotFoundError(...), а один обработчик наверху превращает это в аккуратный JSON.

class AppError(Exception)Базовый класс: атрибуты error_code, http_status, message. Конструктор принимает своё сообщение и опциональный photo_id (уйдёт в лог).
наследникиStorageUnavailable (503), NotFoundError (404), ValidationError (400), ConflictError (409), PayloadTooLargeError (413), UnsupportedMediaTypeError (415), и новый в TASK-002 — BatchSizeError (400, если файлов в батче не 2–10).
register_exception_handlers(app)Регистрирует два обработчика: на AppError — вернуть его error_code/http_status; на любое другое Exception — «страховочная сетка»: залогировать полный traceback для нас, а клиенту отдать сдержанный 500 INTERNAL_ERROR без утечки деталей. Тело всех ошибок единое: {error_code, message, request_id}.
07

schemas: бланки ответов

app/schemas/photos.pyPydantic DTO

Pydantic-модели описывают форму JSON. FastAPI по ним валидирует ответы и строит автодокументацию (/docs).

UploadPhotoResponse{photo_id, status: Literal["pending"]}. Literal["pending"] — тип «строго строка pending и ничего больше»: только что загруженное фото не может быть в другом статусе, это гарантия на уровне типов.
AnalysisResultResponseРезультат анализа: faces_count, is_blurred, blur_score, perceptual_hash. TASK-002.
PhotoResponseКарточка фото: id, filename, status плюс новое поле analysis: AnalysisResultResponse | None = None. Дефолт None — обратная совместимость: старые клиенты, не знающие про analysis, не сломаются.
BatchAcceptedResponse / BatchPhotoItemОтвет на загрузку батча: {batch_id, photos:[{photo_id, status:"pending"}]}.
BatchResponse / BatchPhotoDetailСтатус батча: {batch_id, status, photos:[...с analysis], best_photo_id}. status — Literal["processing","completed"]; best_photo_id заполняется только когда батч завершён.
08

db: база данных

app/db/models.pyORM-модели

ORM (SQLAlchemy) описывает таблицу как Python-класс: строка таблицы = объект класса. Mapped[str] — «в Python это строка, сделай столбец».

class PhotoStatus(str, enum.Enum)Перечисление 4 статусов. Двойное наследование (str, Enum) — трюк: PhotoStatus.pending == "pending" истинно, и в JSON сериализуется само.
class PhotoГлавная таблица. Базовые поля (TASK-001): photo_id (первичный ключ, случайный UUID — не угадать чужие фото), filename, object_key (путь в MinIO, unique=True — защита от дублей на уровне БД), created_at (ставит сама БД), status. Добавлено в TASK-002: attempts, last_error_code, last_error_message (учёт ретраев); publish_status + published_at (outbox); trace_id (сквозная трассировка); batch_id (в каком батче, nullable — у одиночных фото батча нет).
relationship analysis / batchrelationship(...) — не столбец, а «навигация»: photo.analysis даёт связанный объект результата, photo.batch — батч. Загружается заранее (см. репозиторий), чтобы в async-коде не сработала «ленивая» подгрузка.
class AnalysisResultРезультат анализа, 1 к 1 с фото: photo_id одновременно первичный ключ И внешний ключ → гарантирует не больше одной строки на фото (это и делает запись идемпотентной). Поля faces_count, is_blurred, blur_score, perceptual_hash. ondelete="CASCADE" — удалят фото, результат удалится сам.
class BatchБатч: batch_id, status (VARCHAR + CHECK, не enum — см. ниже), best_photo_id (nullable, внешний ключ на лучшее фото), created_at. Связь photos с order_by="created_at, photo_id" — детерминированный порядок в ответе (фикс ревью M2).

Почему статусы outbox и батча — VARCHAR + CHECK, а не enum? В TASK-000 был баг: enum создавался в миграции дважды и падал. Чтобы не повторять класс бага, новые статусы сделаны обычными строками с проверкой CHECK (status IN (...)).

get_session()FastAPI-зависимость: на каждый запрос выдаёт свежую сессию через yield и закрывает после ответа. Важно: тут нет commit/rollback — кто фиксирует транзакцию, решает сервис. Это позволяет откатить всё, если следующий шаг (MinIO/Kafka) упадёт.

services: мозг приложения

app/services/photo_service.pyлогика фото и батчей
_validate(data) → (ext, content_type)Проверка по магическим байтам: первые байты файла (JPEG начинается с FF D8 FF, PNG с 89 50 4E 47…) — единственный честный способ (расширение и заголовок можно подделать). По порядку: пусто → 400, >50 МБ → 413, не картинка → 415.
create_photo(session, filename, data)Главный сценарий загрузки. Порядок flush БД → MinIO → commit: сначала вставка (не коммит), потом байты в MinIO (в отдельном потоке, под таймаутом 60с), потом commit. Если MinIO упал — rollback (строки как не было, битой записи не остаётся) и 503. В той же транзакции ставит publish_status='not_sent' и trace_id — Kafka здесь не трогается вообще, её дело — outbox.
create_batch(session, files)Батч 2–10 файлов, атомарно. Две фазы: (1) провалидировать все файлы и проверить суммарный размер (>500 МБ → 413) — до любой записи; один плохой файл отклоняет весь батч, ничего не сохранено. (2) создать батч и по фото на файл, сохранить в MinIO. Сбой на середине → rollback + удаление уже сохранённых объектов (компенсация). Каждое фото помечается not_sent → уйдёт в конвейер через outbox.
get_photo / list_photosЧитают из репозитория, мапят в PhotoResponse. Хелпер _analysis_response() кладёт результат анализа в поле analysis (или None, пока не done).
get_photo_content(...)Достаёт байты из MinIO (тоже поток + таймаут), возвращает (data, content_type, filename) для отдачи файла.
app/services/batch_service.pyлучший кадр
select_best_photo(photos) → uuid | NoneЧистая функция (без БД, легко тестируется). Берёт только фото со статусом done и выбирает лучшее по формуле-ключу: is_blurred ↑ (не размытое лучше) → blur_score ↑ (меньше размытия) → faces_count ↓ (больше лиц) → created_at ↑ → photo_id ↑ (финальный детерминированный тай-брейк, фикс M1). Все failed → None.
BatchService.get_batch(...)Собирает агрегатную картину батча. Если все фото терминальны (done/failed) → completed, считает best_photo_id и (при первом переходе) сохраняет его в БД. Иначе → processing, best_photo_id = None. Нет батча → 404.
app/services/outbox.pyфоновый publisher · TASK-002
run_outbox_publisher(...)Фоновая asyncio-задача, запущенная из lifespan api. Цикл: ensure_started() продюсера → выбрать строки not_sent → опубликовать каждую в Kafka → пометить sent. Если Kafka недоступна — строка остаётся not_sent (не падаем, счётчик kafka_publish_errors_total, повтор на следующей итерации). Это единственный путь публикации в Kafka. Останавливается по stop_event (graceful shutdown).

Почему так: загрузка (HTTP) никогда не блокируется и не падает из-за Kafka — она лишь ставит пометку в БД, а доставку берёт на себя фоновая задача. Это даёт гарантию «at-least-once» без Kafka в горячем пути запроса.

app/services/analysis_processor.pyядро воркера · TASK-002

Обработка одного сообщения. Вынесено из consumer'а, чтобы тестировать без Kafka. Не знает про Kafka и HTTP — получает сессию и данные.

process(session, photo_id, object_key)Три шага. 1. Захват: claim_for_processing; если 0 строк — дубль, лог + worker_messages_processed_total{result=skipped}, выход. 2. Анализ с ретраями: цикл до WORKER_MAX_ATTEMPTS, вызов gRPC под таймаутом; при ошибке — classify_grpc_error, запись record_attempt, и либо стоп (NO_RETRY или исчерпан лимит), либо пауза backoff·2^(n-1) (1-2-4 сек) и повтор. 3. Терминал: успех → upsert результата + mark_done → done; иначе mark_failed с причиной no_retry/retries_exhausted → failed. По ходу инкрементит метрики и меряет длительность.

worker: обработчик очереди

Второй «вход» в приложение — отдельный контейнер из того же образа, но запускается как python -m app.worker.main. Не слушает HTTP, а бесконечно читает Kafka.

app/worker/main.pyточка входа воркера
_run()Сборка: настроить логи, поднять свой HTTP-сервер метрик на порту 8001 (start_http_server), создать gRPC-клиент и AnalysisProcessor, подключить Kafka-consumer (enable_auto_commit=False — offset коммитим сами, auto_offset_reset="earliest" — читать с начала, если группа новая), запустить consume_loop.
_install_shutdown_handlers(stop_event)Ловит SIGTERM/SIGINT → ставит stop_event для graceful shutdown. На Windows (нет POSIX-сигналов) откатывается на signal.signal.
graceful shutdown (finally)По сигналу: доработать текущее сообщение → consumer.stop() (коммит последнего offset) → analyzer.close() (закрыть gRPC-канал) → engine.dispose() (закрыть пул БД).
app/worker/consumer.pyцикл чтения очереди
consume_loop(consumer, processor, stop_event)Пока не пришёл сигнал остановки: взять сообщение (getone с таймаутом — чтобы между сообщениями проверять stop_event), обработать, потом закоммитить offset. Порядок «сначала обработать, потом коммит» = at-least-once: если воркер упадёт до коммита, Kafka пришлёт сообщение снова, а идемпотентный захват сделает повтор безопасным.
_handle_message(message, processor)Разобрать JSON. «Ядовитое» сообщение (нечитаемый JSON, или нет/пусто photo_id/object_key) — залогировать и пропустить (offset всё равно закоммитится), а не зависнуть на нём навечно (фиксы reviewer-2). Достать trace_id из сообщения в contextvar, открыть сессию, отдать в processor.process; любую неожиданную ошибку поймать, чтобы один сбой не убил весь цикл.

Обе картины целиком

Что происходит при curl -F "file=@a.jpg" .../v1/photos

  1. uvicorn принимает соединение, передаёт в приложение.
  2. RequestIdMiddleware генерит request_id, кладёт в contextvar; metrics_middleware засекает время.
  3. Роутер зовёт upload_photo; FastAPI готовит зависимости (сессия, сервис).
  4. Сервис смотрит первые байты → JPEG; генерит photo_id, путь photos/{id}/original.jpg.
  5. Репозиторий: INSERT + flush (со статусом pending и publish_status=not_sent).
  6. Storage (в потоке, под таймаутом): байты в MinIO.
  7. Сервис: commit. Ответ 202 {photo_id, status:"pending"}, middleware дописывает X-Request-ID.

Что происходит дальше, в фоне

  1. Outbox (фоновая задача api) видит строку not_sent, публикует {photo_id, object_key, created_at, trace_id} в Kafka, ставит sent.
  2. Worker читает сообщение, атомарно claim_for_processing: pending → processing (1 строка = выиграл).
  3. gRPC: воркер шлёт object_key анализатору, получает {faces_count, is_blurred, blur_score, perceptual_hash}.
  4. БД: upsert результата + mark_done → done. Offset коммитится после обработки.
  5. Клиент: GET /v1/photos/{id} теперь отдаёт done с полем analysis.

А если анализатор временно лежит — воркер повторит до 3 раз с паузами, и лишь потом переведёт в failed с last_error_*. Если Kafka лежала при загрузке — фото просто дольше побудет pending, пока outbox не дошлёт задачу. Ни битых данных, ни потерянных задач, ни зависших HTTP-запросов.

Одной фразой

Олимпиадная программа — это функция (вход → выход). Бэкенд — это организация: штат ролей с регламентами на случай ЧП, очередью между цехами и журналом учёта, которая обслуживает поток клиентов без выходных.
